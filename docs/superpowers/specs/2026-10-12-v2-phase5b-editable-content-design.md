# v2 Phase 5b — Editable Wording, Stud Listing Terms and History — Design

**Date:** 2026-10-12
**Status:** Approved (2026-10-12). Built on `feature/v2-phase5b-editable-content` (2026-10-13); not merged. See the plan's "Plan decisions" and "Changes made during the build" (25 keys; Convert to Make an Offer is also gated; terms markdown filters unsafe links).
**Branch:** `feature/v2-phase5b-editable-content` (from master after Phase 5a merged as PR #7)
**Builds on:** `2026-10-09-business-model-v2-design.md` ("all policy and T&C wording is configurable content";
GST option (a): the stud agrees under the listing-fee terms that the buyer fee comes out of its price),
`2026-10-11-v2-phase5a-intro-offers-tax-invoices-design.md` (5b scope), Phases 3–4 (emails).

## Goal

1. Staff edit the **buyer disclosure wording** and the **wording of every system email** without a deploy.
   Changes are versioned; older versions can be viewed and restored.
2. Staff publish versioned **stud listing terms**; a stud must accept the current version before paying a
   listing fee or publishing a listing.
3. Staff can see the **T&C version history** (buyer and stud) and a **change log** of settings, fees, business
   details, intro offers, wording and terms.
4. Fix the Phase 5a follow-up: a failed unit of work leaves the change tracker clean.

## Decisions (agreed 2026-10-12)

| # | Decision |
|---|---|
| 1 | Emails: Staff edit the **subject and message text** with fixed placeholders. The amounts table, links/buttons, the mandatory buyer-fee disclosure block, invoice details and the layout stay generated by code. |
| 2 | Wording is **versioned**: each save is a new version (who, when); the newest is current; old versions can be viewed and restored (restore = publish the old text as a new version). Nothing records which version a buyer saw. |
| 3 | **Stud listing terms** are a second T&C stream with acceptance recorded on the **stud farm**, gating Activate (listing-fee payment) and listing Publish. |
| 4 | History views: **T&C versions** (buyer and stud) and a **Change log** of Staff changes. Wording versions are shown inside the wording editor. |
| 5 | Body text is **plain text** (blank line = new paragraph), HTML-encoded on output. No Staff-authored HTML. |

## Content store

### `ContentItem` (new table, one row per version)

| Column | Notes |
|---|---|
| `Id` | Guid |
| `Key` | string ≤ 100, e.g. `Disclosure.BuyerFeeExplanation`, `Email.Outbid` |
| `Version` | int, starts at 1 per key; unique (`Key`, `Version`) |
| `Subject?` | ≤ 200; emails only |
| `Body` | ≤ 4,000 |
| `CreatedAt`, `CreatedByUserId?` | null user for the migration seed |

The current text for a key is its highest version.

### `ContentCatalog` (code)

A static registry, one entry per key: key, group (Disclosures / Buyer emails / Stud emails / Tax document
emails), label, description of when it is sent, whether it has a subject, the **allowed placeholders** with a
sample value each, the **required placeholders**, and the **default subject/body** (today's wording). The default
is used for the migration seed and for "Reset to default". Unknown keys are rejected everywhere.

Keys (final list confirmed against the code in the plan; variants that differ only in wording get their own key):

- **Disclosures:** `Disclosure.BuyerFeeExplanation`, `Disclosure.StudFarmBalanceArrangement`,
  `Disclosure.SavedCardExplanation` — seeded from today's `appsettings.json` `Checkout` section, which is then
  removed along with `DisclosureOptions`.
- **Buyer emails:** `Email.Outbid`, `Email.AuctionLost`, `Email.AuctionEndedWithoutSale`, `Email.WonAndCharged`,
  `Email.OfferAcceptedAndCharged`, `Email.PaymentFailed`, `Email.PaymentAbandoned`, `Email.OfferDeclined`,
  `Email.OfferExpired`, `Email.OfferExpiredListingClosed`.
- **Stud emails:** `Email.StudSaleConfirmation`, `Email.StudNoSaleAuction`, `Email.StudNoSaleMakeAnOffer`,
  `Email.OfferReceived`.
- **Tax document emails:** `Email.ListingFeeTaxInvoice`, `Email.ListingFeeInvoiceDue`, `Email.ListingFeeReceipt`,
  `Email.BuyerFeeTaxInvoice`, `Email.AdjustmentNote`.

### Placeholders

Syntax `{Name}`; names are case-sensitive. Each email's catalog entry lists its own set, drawn from:
`{StallionName}`, `{Season}`, `{StudName}`, `{BuyerName}`, `{Amount}` (formatted money), `{HighBid}`,
`{ClosesAt}` (Sydney date/time), `{Deadline}` (grace / expiry, Sydney), `{InvoiceNumber}`, `{OriginalNumber}`,
`{DueDate}`, `{Reason}`. Values are computed by the email code exactly as today.

- **Save validation:** reject a placeholder not in the item's allowed list ("{Foo} isn't available in this
  email"), a missing required placeholder, an empty body, an over-length subject/body, and unbalanced braces.
- **Rendering:** substitute values, HTML-encode the result, split on blank lines into paragraphs. Values are
  encoded too. Line breaks inside a paragraph become `<br>`.
- Disclosure items have no placeholders.

### `ContentService`

- `GetAsync(key)` → current subject/body (version). A 60-second in-memory cache per instance; a save clears this
  instance's cache. (Other instances pick the change up within 60 s — acceptable.)
- `RenderEmailAsync(key, values)` → subject + paragraph HTML, used by `AuctionEmails` and `TaxDocumentEmails`.
  The generated blocks (amounts table, buttons, disclosure block, invoice table) are appended by those classes
  around the rendered text exactly where today's wording sits.
- Staff: `ListAsync()` (catalog + current version, changed at/by), `GetHistoryAsync(key)`, `SaveAsync(key,
  subject, body)` → new version, `RestoreAsync(key, version)`, `ResetAsync(key)`. All audited
  (`ContentItem` entity, action `UpdateWording`, old/new text).
- Readers of the old `DisclosureOptions` (`DisclosuresController`, `AuctionEmails`, `TaxDocumentEmails`,
  `TaxDocumentQueryService`) switch to `ContentService`.

## Stud listing terms

- `TermsDocument` gains `Audience` (`Buyer` / `Stud`, string, required). Migration sets existing rows to `Buyer`.
  Version numbers are per audience; unique (`Audience`, `Version`).
- `StudFarm` gains `AcceptedStudTermsVersion?`, `AcceptedStudTermsAt?`, `AcceptedStudTermsByUserId?`.
- API: existing buyer endpoints keep their behaviour (audience Buyer). New: `GET api/terms/stud/current`
  (StudFarmOrStaff), `POST api/terms/stud/accept` (StudFarmAdminOnly — records the current version on the caller's
  farm, audited), and `audience` on Staff publish / history.
- **Gate:** `SubscriptionService.ActivateAsync` and the listing **Publish** path reject a stud admin whose farm has
  not accepted the current stud terms: 400 "Accept the current stud listing terms first." When no stud terms are
  published, there is no gate. Staff actions are never gated.
- Client: the stud's My Stallions (Activate) and listing Publish show a **Stud terms** modal (markdown rendered,
  "I accept") when acceptance is needed, then continue. Staff → Stud farms shows each farm's accepted version/date.

## History views

- **Terms:** Staff → Terms gets a Buyer / Stud switch and a version list (version, published by, date) with a
  read-only view of any version. `TermsService.PublishAsync` now writes an audit row (`PublishTerms`).
- **Change log** (`/staff/change-log`, new nav link; `GET api/audit/changes`, StaffOnly): reads audit rows for
  these areas — platform settings, business details, intro offers, wording, terms publish, stud terms accepted.
  Columns: when (Sydney), who, area, item, what changed (old → new per changed field; unchanged fields hidden).
  Filters: area, from/to (Sydney dates). Paged, 50 per page, newest first. Bank account numbers are masked to the
  last 3 digits in this view (the stored audit row is unchanged). Long text values (wording, terms) show a
  "changed" marker with a link to the version instead of the full text.

## Staff → Wording (`/staff/wording`, new nav link)

- List grouped by area: label, description, current version, changed at/by.
- Editor: subject (emails), body, the placeholder list with descriptions, a live **preview** using the catalog's
  sample values (rendered by the same server code via `POST api/content/{key}/preview`), **Save as new version**,
  **Reset to default** (confirm), **Previous versions** (view, restore with confirm). Validation errors from the
  server shown inline.

## Phase 5a follow-up

`EfTransactionRunner` clears the change tracker when a unit of work throws (before rethrowing), so nothing a
failed item tracked is saved by a later `SaveChanges` (e.g. the "Issue missing tax invoices" aggregate audit).
Test: an item that tracks an entity then throws; the aggregate audit save doesn't persist it.

## Security

- All new endpoints authenticated; wording, preview, terms publish/history and change log are **StaffOnly** and
  re-checked in the service. Current disclosure text (`api/disclosures/buyer-fee`) and current stud terms remain
  readable by the roles that need them.
- Plain-text bodies, HTML-encoded on output (emails and pages) — Staff can't inject markup or script; terms keep
  the existing markdown renderer and its sanitisation.
- Placeholder values are encoded; unknown keys rejected; length limits enforced client- and server-side.
- Every save / restore / reset / publish / acceptance is audited.

## Errors

- Missing content row for a key (shouldn't happen after the seed): fall back to the catalog default and log a
  warning, so an email or disclosure is never blank.
- Placeholder with no value at render time: rendered empty and a warning logged (the catalog's required list makes
  this a programming error, caught by tests).

## Testing (test-first)

- Catalog: every key has a default that passes its own validation; every placeholder the email code supplies is in
  the catalog and vice versa.
- `ContentService`: versioning, cache and invalidation, restore/reset create new versions, audit, Staff-only.
- Placeholder validation and rendering (unknown, missing required, braces, encoding, paragraphs).
- Each email built with **edited** wording still contains its generated parts (amounts table, disclosure block,
  buttons, invoice link) and the substituted values; with default wording the output matches today's text.
- Disclosure endpoint and tax document fee note read the stored text.
- Stud terms: publish per audience, accept, gate on Activate and Publish (not accepted / accepted / new version /
  none published / Staff not gated).
- Change log: area filters, field diff, masking, paging, Staff-only.
- Transaction runner clears the tracker on failure.
- bUnit: Wording list and editor (validation, preview, restore, reset), Terms switch and history, Change log,
  stud terms modal on Activate and Publish, Stud farms acceptance column.
- Migration: `ContentItems` seeded with the defaults (version 1, null user), `TermsDocuments.Audience` = Buyer
  for existing rows, stud farm columns. Dev database only.

## Out of scope

- Recording which wording version a buyer saw; HTML or rich-text email editing; per-language wording.
- Editing email layout, the amounts table, or the disclosure block's structure.
- Re-accepting buyer T&C flows (unchanged).
- Multi-instance cache push (60-second expiry is enough).
